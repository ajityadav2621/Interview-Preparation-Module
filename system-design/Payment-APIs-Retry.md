# Payment APIs with Retry and Duplicate Handling

## Requirements
- Safe retry mechanisms
- Idempotent operations
- Duplicate request detection
- Error handling

## Design Patterns

### 1. **Idempotency Keys**
```java
@POST("/payments")
public ResponseEntity<PaymentResponse> createPayment(
    @RequestHeader("Idempotency-Key") String idempotencyKey,
    @RequestBody PaymentRequest request) {
    
    // Check if request already processed
    Payment existing = paymentService.findByIdempotencyKey(idempotencyKey);
    if (existing != null) {
        return ResponseEntity.ok(existing);
    }
    
    // Process new payment
    Payment payment = paymentService.process(request, idempotencyKey);
    return ResponseEntity.ok(payment);
}
```

### 2. **Database Constraints**
```sql
CREATE TABLE payments (
    id BIGSERIAL PRIMARY KEY,
    idempotency_key VARCHAR(255) UNIQUE NOT NULL,
    amount DECIMAL(10,2) NOT NULL,
    status VARCHAR(50) NOT NULL,
    created_at TIMESTAMP DEFAULT NOW()
);
```

### 3. **Retry Strategy**
```java
@Retryable(value = {PaymentException.class}, 
           maxAttempts = 3, 
           backoff = @Backoff(delay = 1000))
public Payment processPayment(PaymentRequest request, String idempotencyKey) {
    // Payment processing logic
}
```

## Interview Tip
Explain that payment APIs must be idempotent by design. Mention that idempotency keys should be generated by the client and stored with the transaction.
